# Remote two-player playtest — 2026-11-04

First playtest with an outside player on their own machine. **It went well.** Both players stayed connected for about two hours and the server never crashed. The session ended with a normal `stop` that saved the world. Both players said they liked it ("pretty sick", "super sick"). They called out the schematic paste feature as a highlight.

## Setup

- **Server:** an ordinary development dedicated server (the `exportLocalPlayLaunches` server launch, no GameTests), run from `run-multiplayer/playtest/server`. Port 25565, `server-ip` blank so it listens on every interface, `online-mode=false`, space start with the Sparrow starter ship. The launcher was a one-off copy of `testt-server.ps1`'s server half without the loopback bind or the two scripted clients. It is not checked in.
- **Remote client:** Modrinth App instance with Minecraft 26.3, Fabric Loader 0.19.5, and Fabric API for 26.3. The built `build/libs/nullspace-0.1.0.jar` went into the instance's mods folder. No other mods were needed.
- **Host client:** the development client as `Player451`.
- **Connectivity:** both players connected through the public IP, not Hamachi. Router port forwarding of 25565 worked.

## Errors

### `Block-attached entity at invalid position: null` (36 lines, vanilla)

These came in four bursts of 9 at 21:53:40, 21:53:42, 22:22:01 and 22:22:03. Each burst came from Nevulaa's command-based schematic paste. Every error comes right before a `Summoned new Item Frame` line, inside a run of `setblock`/`fill` output. The paste summons item frames before (or without) the blocks they hang on, so vanilla rejects the frames. This is not a NullSpace bug.

**Follow-up:** check in game whether those item frames are missing from the pasted builds. If the paste tool is ours or will be shipped with the mod, it should place blocks before block-attached entities (item frames, paintings).

### Docking: "Docking port controller is missing" (4)

At 21:03:46, 21:10:14, 21:10:38 and 21:13:27, ship `Yard Halcyon Courier` was stuck `CLAMPED` at `Player451 Station` port (0, 2, 8), piloted by Player451. In the minute before:

- 21:02:11 `A nearby hull obstructs undocking`
- 21:03:18 `Place a framed standard door directly above the Docking Base`
- 21:03:21–21:04:09 there were 12 vanilla `Mismatch in destroy block pos` warnings around x=8190–8192, y=98–103, z=8–10, at the station port

**Cause (confirmed by the players):** the new station flow. They created a new station, and that worked. They built a docking room, and that also worked. The room's blocks overlapped the docking area. The Courier still docked, and players could walk through the dock without trouble. Undocking, though, saw the room as a "nearby hull obstructing undocking", so the ship couldn't leave. To free it, they broke the dock: first the door, then the port controller. That made it worse: the Courier stayed `CLAMPED`, and every docking update afterwards failed with "controller is missing". The destroy-pos mismatches are from that demolition.

**Follow-ups:**
1. **Station flow UX.** Building or validating a docking room should refuse, or clearly warn, when it overlaps a port's docking or undocking clearance. Nothing currently tells the player that docking will succeed but undocking won't.
2. **Undock clearance should agree with docking clearance.** If a ship could mate and players can walk through the port, the station's own room should not count as an obstruction for the departure path. Otherwise, check both the same way, so a ship can never dock somewhere it can't leave.
3. **Recovery from a broken port.** A clamped ship whose port loses its door or controller should release, or be force-undockable from the ship controller, instead of staying `CLAMPED` forever. Removing the obstruction should also be enough to let it undock.
4. Check whether the Courier is still stuck in the saved world. If so, the only way out today may be ship recall from a Pad Computer.

### Other

- **Offline-mode warnings (4 lines).** Expected with `online-mode=false`.
- **`/op ls` typo.** At 20:39:38 someone ran `/op ls`, which made `ls` an operator. `Zero_sum` was also opped. `ops.json` still lists both. Because offline mode doesn't check identities, anyone who joins with those names gets op. Run `/deop ls` (and `/deop Zero_sum` if that was unintended) before the next session.
- **Fabric dev warnings.** `Untranslated Item Tags detected` and `Ignoring invalid library path $env:PATH` appear on every development run. They are harmless.
