# Feature-freeze repository review — November 18, 2026

This replaces the preliminary cleanup assessment at the top of [test-audit.md](test-audit.md). Review baseline: `df3ea7c` (0.8.0 release record). The working changes are an audit and maintenance batch, with no new gameplay or performance tuning.

## Review scope and evidence

Read all **48 design documents**, all **273 Java test and helper sources** (102 unit-source files, 166 GameTest files, five compatibility files), and the test scripts, shared PowerShell modules and CI workflows. [Design review inventory](design-review.csv) records each design document. [Test review inventory](test-review.csv) records every Java test-source file, its declared cases, disposition and source hash. Declared method counts are not runtime execution counts.

The production review traces initialization, server lifetime, persistence/recovery, physical transfers, topology, engineering, computers, flight/FTL, docking, planets, crash starts, hab registration/doors, materials, defence, trees, bosses, population and scene delivery. Recent feature context is the 0.6.0 generation/loot/scanner change (`52d8b2b`), 0.6.1 enemies (`b25892e`), 0.7.0 starts/flight (`f9f1b99`), 0.8.0 rewards/habs (`438b2e7`) and its subsequent correctness/harness fixes. This is not a claim that every production source line, generated asset or historical commit was independently verified.

No new coverage percentage or mutation score was measured. The November 14 numbers remain historical. Prior passing release receipts do not certify these working changes. Fresh validation for this batch is recorded below.

## How the systems connect

| Boundary | Current ownership and behavior | Why its tests stay |
| --- | --- | --- |
| Startup and lifetime | `NullSpace.onInitialize` registers services; `ServerContext` owns per-server runtime state. Its phases end in `FIXTURES → SAVE`; `BuildJournal` uses SAVE for batched completion. Native block entities and some content also tick outside that dispatcher. | Client lifecycle tests open several worlds in one JVM and inspect actual resource destruction. A clean single startup cannot substitute for them. |
| World metadata | `WorldStore` exposes borrowed mutable records through `ShipRepository`. `StoreSlots` alternates `ships-a.nbt` and `ships-b.nbt`; the newest readable save number wins. World-save hooks synchronize chunks and metadata and respect save-off. | Pure codecs, actual compressed NBT, native save hooks and fresh-process recovery test different boundaries. |
| Transactions | MOVE captures hull, scheduled ticks, entities, crew and changed records before destructive edits. BUILD captures construction footprints and batches completed jobs behind a world-save barrier. RECORD commits metadata changes without forcing a world save. `TransferRecovery` contains failures per journal and retains locks for unresolved work. | Legacy format fixtures remain compatibility tests. Killing a fresh JVM at a checkpoint exercises durability that an injected in-process exception cannot establish. |
| Launch and landing | `ShipService.preflight` checks the real hull/occupants; `TravelService` performs client readiness and arrival handshakes; `ShipTransfer` places/clears through `TransferReplay`. Landing rotation follows the entrance and the pad computer's edge. | Unit transforms complement native blocks, inventories, passengers, leashes, mounts, ticks and offline arrival tests. |
| Topology and engineering | `ShipTopology` discovers connected equipment independently of strict travel validation. `ShipSystems` coordinates device identity, integer power/fuel, doors and finite spatial air. Runtime source-record identity prevents using caches after record replacement. | Conservation, quotas and topology tests are fast model contracts; native tests establish real fuel containers, hoppers, block hooks and permissions. |
| Large habs | `HabVessels` records a hab's own blocks so discovery does not absorb surrounding rock. Large grids retain compressed air/seals and candidate devices. Loaded device chunks participate; the controller chunk permits the station to run. Full air rebuilds can run on a worker. | Preserve the recent structural rebuild assertions and door invalidation fixes. | Flight and FTL | Physical storage slots and simulated pose are separate. `NavigationService` applies mass/thrust/spin/fuel; releasing a lease retains momentum and unattended assist brakes when possible. | Docking | `DockingService` delegates reservations and guided motion to `DockingManeuver`; `Boarding` moves players between separately stored vessels. Collars are journaled physical edits. | Generation and encounters | `StationPlanner` creates a validated seeded room plan; structure/furnishing passes produce blocks and entity points. Planned ships reuse station construction; tiny ships and player-built tile stations retain separate live paths. `SpacePopulation` records sites before asynchronous planning/queued placement and preserves depletion/removal until reset rules apply. | Keep old and new generator suites while their player/command paths remain supported. Geometry, placed structures, loot rolls and actual walking are separate checks. |
| 0.7 starts and planets | `SpaceStart` dispatches saved settings; `CrashStart` allocates a site, builds through BUILD, damages it and records completed supplies/crew. `PlanetDimensions` recreates dedicated surfaces before recovery; legacy assignments remain supported. | Native idempotence, single/multiple crews, GUI world creation and fresh-process planet identity each test different dependencies. |
| 0.8 rewards | Richness modifies planet ore attempts/heights; geodes/fluid are registered content/data. Turrets use real target visibility and fuel; repair bays pay a job's fuel before repair. Trees persist game-time growth; the boss nest tracks its live UUID and daily respawn. | Retain recipe/drop, native inventory/entity, air/explosion, power and persistence tests. These do not establish reward balance or generated-world frequency. |
| Scene rendering | Server scene leases send bounded block/light/visual snapshots and pose updates. Client viewport/compute passes own actual GPU resources. Screenshots alone require review. |

Registered is not the same as exercised. There are **106 registered native classes / 369 annotated methods** and **45 registered client classes** in this batch. Crash/restart, performance, survey and video entrypoints may immediately succeed without their activation properties. Screenshot galleries check successful construction/rendering but do not automatically judge design quality. The inventory marks those distinctions. No disabled annotation does not mean every intended regression runs: the computer-slot regression below is deliberately unannotated.

## Coverage gaps and refactor queue

These are follow-ups, not claims of reproduced failures or additions made during final verification:

- **Hab lifetime:** `aHabKeepsItsLightWhenItsChunksUnloadAfterTheBuildAndLoadAgain` waits and requests chunks but never establishes that unloading occurred. Golden-tree catch-up advances saved time through `awayFor`, rather than closing/reopening a world. Partial hab loading, powered door fallback and device participation deserve one coherent lifecycle scenario. `HabVessels.OWN` is a static cache keyed only by vessel id; assess cross-world lifetime separately.
- **World generation:** ore richness math/registration is covered; actual generated ore/geode/debris density by distance is not established. The band test accepts zero as an alternative to the expected band. `AirlessCrewsGameTest` places mobs with COMMAND, so it does not establish natural spawn placement.
- **Meaningful minima:** entity sweeps skip types that cannot be created; the transient-type subset assertion alone can pass with no observations. Village-port client review may accept `no_site` without rendering a port. Station expansion's unit name promises eight berths but checks room/joint counts; native berth-envelope coverage is separate.
- **Repair acceptance:** the repair test checks retained enchantments, repair and spent fuel; it does not remove/exhaust fuel. Add the refusal branch when working on that contract, rather than claiming the existing case covers it.
- **Fixture isolation:** some native fixtures mutate clocks, claiming flags, registries or forced chunks with success-only cleanup. Preserve deliberate slot reservations until hull/entities are removed. A safe fixture refactor must account for failure callbacks and CI shard membership together.
- **Production refactors:** `StationStructure`, `DerelictDamage`, `ShipTransfer` and gallery construction are large, but size alone is not a freeze-safe extraction rationale. Prefer named generation passes and explicit fixture ownership in later batches with real behavioral dependencies. Do not optimize the hab/air/save paths from timing guesses.
- **Compatibility:** accepted Waystone identity replacement remains a limitation. Registry sweeps cannot establish arbitrary mod AI, world-position databases or every interaction. Keep mod-specific database/ticket cases.
- **Player acceptance:** sealed rooms, BFS routes, light values, screenshots and a passing launch do not establish enjoyable stations, readable navigation, reward balance or survival pacing. Review actual generated builds and player actions for those decisions.
