# Test hygiene: why a GameTest must not fail at random

The native GameTests run about ninety at a time on one server in one world, so a test that is right alone can fail now and then in the full run. That costs a whole [release check](local-verification.md#the-release-check) (about 25 minutes) to find, and finds one failure at a time. In November 2026 two release checks in a row failed on different tests that passed alone. Both had the same two causes, and [`GameTestHygieneTest`](../../src/test/java/com/nullandkale/nullspace/testing/GameTestHygieneTest.java) now fails the build on them, in the unit tests that run first, in seconds.

## The rules

1. **Do not drop the answer of a pad registration.** A registered pad outlives its test, every batch of tests is laid out over the same ground, and [`PadComputers.register`](../../src/main/java/com/nullandkale/nullspace/gameplay/pads/PadComputers.java) refuses (it returns the reason as text) when an earlier test's pad has the same name or overlaps the ring. A test that ignored the text failed later, somewhere else, with "Register the pad below this ship first". Use [`TestPads.register`](../../src/gametest/java/com/nullandkale/nullspace/testing/TestPads.java): it removes pads left by tests that have finished, never one that a running test owns, and throws with the reason when the registration is refused. A pad is known to be finished when every test that was running when it appeared is done (batches run one after another, so a pad from an earlier batch always is), or when its computer is gone or in an unloaded chunk. Judging by the computer alone was not enough: many tests leave their chunks forced, a pad left that way kept its computer standing, and in a later batch it refused a defence test's pad laid on the same ground (0.8.3). The rule also finds a dropped registration written with the full package name.
2. **A test that changes what its neighbours see runs in its own environment.** Launching or landing a ship by any path ([`TravelService.transfer`](../../src/main/java/com/nullandkale/nullspace/gameplay/travel/TravelService.java), or a `request` and its `ready` acknowledgement, which transfer a few ticks later) takes the first free orbit slot; setting any static field of a game class (the failure hook, the write observer, [`ShipYardService.placementObserver`](../../src/main/java/com/nullandkale/nullspace/gameplay/shipyard/ShipYardService.java), or one added later), turning saving off, or recovering every journal changes the world for the tests running beside it. Give it `@GameTest(environment = "nullspace:<name>")` and a file `<name>.json` in [`test_environment`](../../src/gametest/resources/data/nullspace/test_environment) (the body of any of them will do). Each environment runs after the shared batch and apart from the others, but the tests that share one run beside each other: a test that picks its orbit slot itself ([`TransferLocks.spaceSlotFree`](../../src/main/java/com/nullandkale/nullspace/gameplay/travel/TransferLocks.java)) and holds that chunk expects its launch to take that slot, so it needs an environment to itself (`concurrent_ship_actions` excepted, which exists to test launches side by side).
3. **Wait for loading, not for ticks.** Entities and chunks load on other threads and a test server never sleeps between ticks, so `runAfterDelay(10, ...)` is a few milliseconds. A test that launched when the machine was idle and came back "Ship passengers are still loading" when it was busy. In a file that launches, lands or recovers ships, wait with [`TestWaits.afterLoaded`](../../src/gametest/java/com/nullandkale/nullspace/testing/TestWaits.java): it waits at least the ticks you give and then until every chunk the test holds, here and in space, has its entities. Hold a chunk with `TestWaits.hold(ctx, level, x, z)`, not `setChunkForced`, so the wait knows which chunks are the test's: many tests force chunks and never release them, and a chunk an earlier test left forced says nothing about this test's fixture. The test's own tick limit ends a wait that never finishes, and the wait sleeps 100 ms between looks, so that limit is seconds of real time and not the few milliseconds a test server's unthrottled ticks take: on a busy machine the threads that load are starved, and a wait counted in ticks alone ran out before they finished (a test whose 200 ticks passed in eight seconds). A test that waits for loading in a file that holds chunks needs `maxTicks` of at least its fixed waits plus 300 ticks (about thirty seconds of real time at the 100 ms pause): a limit of 100 ticks ran out on a busy machine before the entities were loaded. A wait that is about time passing, not about loading (a protocol timeout expiring, a countdown running out), uses `TestWaits.afterTicks`: it says so, and a test that waits for a timeout must not wait for chunks that it left unloaded on purpose.

4. **A wait never gives up and carries on.** `if (ready || waited >= 150) then.run()` goes ahead without what it waited for once a count of ticks runs out, and ticks pass at no fixed speed: on the slower release CI runner, mobs spawned on Ares had not been tagged as crew when the count ran out, died as ordinary mobs, and the test failed on "drops copper over a dozen kills", nothing to do with the cause (0.8.3). Wait for a condition on something that loads on other threads with `TestWaits.until(ctx, ready, then)`: it looks every tick, pauses 100 ms between looks like `afterLoaded`, and ends only by the test's tick limit, so a test that uses it needs the same `maxTicks` of its fixed waits plus 300. A poll for work done on the server tick (a station build, a filling room) may count its tries, but must then fail with a message that says what never came.

5. **Never hand a callback back to the scheduler from inside itself.** The framework keeps scheduled callbacks in a map keyed by the `Runnable` and removes the entry of the one it has just run, so `poll[0] = () -> { ... ctx.runAfterDelay(5, poll[0]); }` is dropped the first time it reschedules, and the poll silently stops: the test waits out its tick limit. This hid in a wait that only rescheduled when a chunk was slow to load, so it passed on an idle machine and timed out on a busy one. Schedule a new lambda each time: `ctx.runAfterDelay(5, () -> poll[0].run())`.

The test also checks that every environment a test names has its file, and that the scan still sees the tests (so a moved folder cannot make the rules pass by finding nothing). Its last test feeds each rule a sample that must be found and one that must not.

## Graphical tests

The graphical tests run one class after another in each of four client JVMs, and the same weaknesses apply in their own form.

- **Wait through [`ClientWaits`](../../src/gametest/java/com/nullandkale/nullspace/testing/ClientWaits.java), not the context.** Fabric's `waitFor` and `waitForChunksRender` count ticks, and a client's ticks pass as fast as frames are drawn: a limit of 200 ticks is a second or two, and on a busy machine the threads that load chunks, build meshes or work out the sky are starved while the ticks race on. `ClientWaits.waitFor` and `ClientWaits.chunksRendered` are Fabric's own waits, failing with the same message, except that a timeout counts only after 60 seconds of real time.
- **Clear the overlays before typing.** The keyboard handler drops characters typed under an overlay without a word, and the loading overlay fades out over a second of real time: a test that typed there would fail later, somewhere else. Call `ClientWaits.withoutOverlay` before every block that types with `keyboardHandler.textInput`.
- **Never wait for real time.** A wait whose condition is `System.nanoTime()` passing a mark is a different length on every machine. The 600 ms pauses this replaced were waiting out the server's limit of one pad or ship action per half second, which was counted in wall-clock time alone; [`ActionLimit`](../../src/main/java/com/nullandkale/nullspace/core/ActionLimit.java) now refuses an action only while both fewer than ten server ticks and less than half a second have passed, and the test waits ten ticks. (Counted in ticks alone, a lagging server refused for longer than a healthy one.) Wait for what a pause was for, or for game ticks with `waitTicks`.
- **A wait that times out says what it saw.** `ClientWaits.waitFor` adds the screen, a terminal's status and rows, any overlay and the player's position to the timeout, so a failure in the release check can be read from its log and not found out by running it again.

[`GameTestHygieneTest`](../../src/test/java/com/nullandkale/nullspace/testing/GameTestHygieneTest.java) fails on a direct context wait, on typing without the overlay wait, and on a wait for real time.

A failing graphical class ends its client JVM, and Fabric runs none of the classes after it. [`parallel-test.ps1`](../../scripts/test/parallel-test.ps1) therefore starts a client for the classes that did not run (the failed one is named by the evidence the client left), until every class has run, and reports every failure of the run together. A client that dies before starting any test failed in start-up, which is reported as such and not continued. Fabric itself restores the default game options before each class, so one class's settings do not reach the next.

## Scripts that run a JVM

The restart scripts ([`crash-test.ps1`](../../scripts/test/crash-test.ps1), [`shipyard-crash-test.ps1`](../../scripts/test/shipyard-crash-test.ps1), [`planet-restart-test.ps1`](../../scripts/test/planet-restart-test.ps1)), [`multiplayer-test.ps1`](../../scripts/test/multiplayer-test.ps1) and the smoke server stop ([`Start-LocalPlayServer.ps1`](../../scripts/run/Start-LocalPlayServer.ps1)) wait for a JVM with `Wait-VerificationProcess` from [`LocalVerification.psm1`](../../scripts/lib/LocalVerification.psm1). It fails when the JVM's logs have not grown for three minutes, which is what a hung JVM looks like, or after a cap far beyond a healthy run (30 minutes). A fixed limit measured how busy the machine was: a crash stage that had written its pass marker was killed at 180 seconds while it saved some sixty dimensions on a machine at 95% CPU (0.8.3). [`Test-LocalVerification.ps1`](../../scripts/test/Test-LocalVerification.ps1) checks that the wait passes a process that keeps logging and stops a silent one, and fails on a script that throws when `WaitForExit` with a fixed time of a minute or more runs out. The short grace waits after a process has been told to stop are not that pattern.

## What is exempt

- [`CrashRecoveryGameTest`](../../src/gametest/java/com/nullandkale/nullspace/gameplay/travel/CrashRecoveryGameTest.java) and [`ShipYardCrashGameTest`](../../src/gametest/java/com/nullandkale/nullspace/gameplay/shipyard/ShipYardCrashGameTest.java): their `restart` test returns at once unless a crash script sets a mode, and then runs alone in its own JVM.
- `PerfWorld` and `DevStoryFixture` are fixtures for generated worlds, not tests: they keep registrations whose computers are gone on purpose.

Add an exemption in the test's two sets, with the reason beside it, and nowhere else.

## What the rules do not see

They read source text. A launch that happens in another class and a wait that happens here are not connected, and a wait written some other way than `runAfterDelay` is not found. A wait that carries on is found by its shape, a condition or a counter named for ticks or tries (`waited`, `tries`, `attempts`, `ticks`, `elapsed`, `polls`, `looks`, `ctx.getTick()`) followed by running the rest of the test; a counter by any other name is not. A new kind of shared state needs a new rule. When a release check fails on a test that passes alone, do not fix that one test and run again: find what it shares, search the tests for every other use of it, fix them together, and put the rule here.
